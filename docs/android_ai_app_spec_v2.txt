ТЕХНИЧЕСКАЯ КОНЦЕПЦИЯ ANDROID-ПРИЛОЖЕНИЯ Универсальный AI-чат и
автономная агентная среда разработки

Версия документа: 2.0 Дата: 11 ноября 2026 г.

============================================================ 1.
КОНЦЕПЦИЯ И ЦЕЛИ ПРОДУКТА
============================================================

Приложение объединяет два основных режима:

1.  ЧАТ — обычный диалог с языковой моделью: история, потоковая
    генерация, Markdown, вложения, выбор провайдера и модели.
2.  АГЕНТ — модель получает набор инструментов для работы с файлами
    выбранного проекта: анализирует структуру, читает и изменяет файлы,
    предлагает план, показывает изменения и выполняет действия в рамках
    выданных разрешений.

Основной принцип: приложение работает непосредственно на
Android-устройстве. Запросы к LLM-провайдерам отправляются напрямую из
приложения. Собственный сервер не требуется. В будущем можно добавить
необязательную синхронизацию, но она не должна быть обязательной для
основных функций.

Цели: - независимость от одного поставщика моделей; - отсутствие
обязательной подписки на конкретный сервис; - безопасная работа агента с
локальными проектами; - прозрачный контроль изменений и расходов; -
удобный интерфейс на телефонах, планшетах и складных устройствах; -
возможность расширять приложение без переписывания ядра.

Приложение не должно позиционироваться только как очередной AI-чат.
Основное направление — AI Development Environment for Android.

============================================================ 2.
ПРОВАЙДЕРЫ И МОДЕЛИ
============================================================

На первом этапе поддержать OpenAI-совместимый API. Это позволит
подключать OpenAI, OpenRouter, Groq, DeepSeek и совместимые локальные
серверы, если они доступны устройству по сети.

Отдельными адаптерами подключить: - Anthropic; - Google Gemini.

Архитектура должна позволять добавлять провайдеры без изменения
интерфейса чата и агентного цикла.

Единый интерфейс LlmProvider не должен скрывать реальные различия API.
Для каждого провайдера нужен адаптер, который преобразует запросы и
ответы в общую внутреннюю модель.

Рекомендуемая структура:

core:llm LlmProvider LlmRequest LlmResponse StreamEvent
ProviderCapabilities ToolCall Usage providers/ OpenAICompatibleProvider
AnthropicProvider GeminiProvider

ProviderCapabilities должен описывать: - поддержку потоковой
генерации; - поддержку tool/function calling; - поддержку параллельных
вызовов инструментов; - поддержку изображений и других типов вложений; -
поддержку reasoning-полей, если провайдер их предоставляет; -
максимальный контекст модели; - доступные форматы ответа; - особенности
ограничений и стоимости, если они известны.

Не считать наличие модели в списке гарантией поддержки инструментов.
Перед запуском агентного режима проверять возможности выбранной модели и
показывать понятное предупреждение, если нужная функция не
поддерживается.

Общие события стрима: - TextDelta; - ReasoningDelta; - ToolCallStart; -
ToolCallDelta; - ToolCallEnd; - Usage; - Done; - Error.

Внутреннее сообщение состоит из частей: - Text; - Reasoning; -
ToolCall; - ToolResult; - File; - Image; - Attachment; - Error или
служебные метаданные при необходимости.

Хранить исходные данные вызовов инструментов и результаты отдельно от
отображаемого текста. Не предполагать, что все провайдеры передают
reasoning или tool calls одинаково.

============================================================ 3.
ТЕХНИЧЕСКИЙ СТЕК
============================================================

Основной стек: - Kotlin; - Jetpack Compose; - Material 3; - Navigation
Compose; - Ktor Client либо OkHttp для HTTP и SSE; -
kotlinx.serialization; - Kotlin Coroutines и Flow; - Room для локальной
базы данных; - DataStore для настроек; - Hilt для внедрения
зависимостей; - JGit для Git-операций после проверки совместимости и
производительности на Android; - Android Keystore для защиты ключей
шифрования.

Для криптографии не писать собственные алгоритмы. Android Keystore
использовать для защиты ключа шифрования. Сами API-ключи хранить в
зашифрованном виде. Не использовать устаревшую security-crypto как
фундамент новой архитектуры без проверки актуального статуса библиотеки.
При необходимости дополнительного криптографического слоя рассмотреть
Tink.

Рекомендуемая структура модулей:

app core:model core:data core:llm core:agent core:workspace
core:security core:ui feature:chat feature:workspace feature:agent
feature:settings feature:onboarding

Назначение модулей: - app — точка входа, сборка приложения и
конфигурация зависимостей; - core:model — общие доменные модели; -
core:data — Room, репозитории, миграции и локальное хранение; - core:llm
— провайдеры, запросы, стриминг и нормализация ответов; - core:agent —
цикл агента, инструменты, планирование, лимиты и разрешения; -
core:workspace — безопасная работа с файлами и проектами; -
core:security — шифрование, хранение секретов и проверки доступа; -
core:ui — общие компоненты интерфейса и тема; - feature:* —
пользовательские экраны и сценарии.

Границы модулей должны быть чёткими. UI не должен напрямую обращаться к
провайдерам или файловой системе. Агент не должен самостоятельно
открывать произвольные пути.

============================================================ 4. ДАННЫЕ И
ROOM ============================================================

Предусмотреть таблицы: - providers; - models; - sessions; - messages; -
parts; - workspaces; - permission_grants; - change_sets; -
tool_executions; - usage_records.

Сессия хранит: - выбранного провайдера и модель; - режим (чат или
агент); - привязку к workspace; - состояние выполнения; - суммарный
расход токенов и денег, если цена известна; - дату создания и последнего
изменения.

Сообщение хранит: - роль; - parentMessageId для ветвления; - временные
метки; - состояние генерации; - порядок в сессии.

Parts хранят текст, вызовы инструментов, результаты, вложения и
служебные данные. Структура должна допускать появление новых типов
частей без ломки всей базы.

Миграции Room обязательны с первой версии. Не использовать destructive
migration в релизной сборке. Настроить тестирование миграций и резервное
копирование пользовательских данных.

Состояние агентной сессии сохранять после каждого значимого шага:
получения ответа модели, вызова инструмента, результата инструмента,
подтверждения пользователя и применения изменений. После аварийного
завершения приложение должно восстановить сессию и показать, можно ли
безопасно продолжить работу.

============================================================ 5. СЛОЙ LLM
И ПОТОКОВАЯ ГЕНЕРАЦИЯ
============================================================

Каждый провайдер реализует общий контракт LlmProvider и преобразует
собственный формат API в StreamEvent.

Обработать: - разрывы соединения; - таймауты; - отмену запроса; - ошибки
авторизации; - превышение лимитов; - некорректные или неполные Tool
Calls; - повторное подключение там, где оно безопасно; - частично
полученные данные.

Не повторять автоматически запросы, которые могут привести к
дублированию платных действий или вызовов инструментов, без проверки
состояния операции.

Сделать тесты на сохранённых примерах SSE-потоков каждого провайдера.
Проверять фрагментированные события, некорректный JSON, несколько
вызовов инструментов и обрыв потока посередине ответа.

Для длинных ответов обновлять UI пачками, ориентировочно раз в 50–100
мс, если это улучшает производительность. Разбор Markdown кэшировать или
выполнять инкрементально, чтобы избежать мерцания и тормозов.

============================================================ 6. АГЕНТНЫЙ
ЦИКЛ ============================================================

Базовый цикл:

1.  Собрать контекст: системные инструкции, историю, описание workspace,
    доступные инструменты и разрешения.
2.  Отправить запрос модели.
3.  Получить поток событий.
4.  Если модель запросила инструмент — проверить схему, права, лимиты и
    безопасность аргументов.
5.  Если требуется подтверждение — показать пользователю действие и
    дождаться решения.
6.  Выполнить разрешённый инструмент.
7.  Сохранить результат в историю и состояние сессии.
8.  Вернуться к запросу модели.
9.  Если инструментов больше нет — завершить ход и показать итог.

Обязательные ограничения: - максимальное число шагов на задачу; - бюджет
токенов; - бюджет денег на сессию; - максимальное время выполнения; -
ограничение размера результата инструмента; - ограничение числа
параллельных вызовов; - кнопка «Стоп»; - возможность отменить отдельный
инструмент, если это технически безопасно.

При достижении лимита агент должен остановиться и объяснить причину.
Значения лимитов должны быть настраиваемыми, но безопасные ограничения
включены по умолчанию.

Состояние цикла хранить так, чтобы после перезапуска можно было
восстановить ход работы, не повторяя уже выполненные операции вслепую.

============================================================ 7.
ИНСТРУМЕНТЫ АГЕНТА
============================================================

Первая версия: - read_file — чтение файла; - list_dir — просмотр
директории; - glob — поиск файлов по шаблону; - grep — поиск текста в
файлах; - write_file — предложение создания или полной замены файла; -
edit_file — предложение точечного изменения; - todo_write — обновление
списка задач; - ask_user — запрос уточнения у пользователя.

Позже: - web_fetch; - git_status; - git_diff; - git_log; - git_commit; -
дополнительные инструменты тестирования; - shell через интеграцию с
Termux.

Инструменты чтения можно выполнять без подтверждения в пределах
workspace. Запись, сетевые действия и запуск команд требуют
подтверждения согласно политике разрешений.

Для каждого инструмента определить: - строгую JSON-схему аргументов; -
допустимые размеры входных и выходных данных; - правила проверки
путей; - таймаут; - обработку ошибок; - требования к подтверждению; -
возможность отмены.

Результаты инструментов считать данными. Не исполнять текст из файлов
или веб-страниц как инструкции.

============================================================ 8.
WORKSPACE И БЕЗОПАСНОСТЬ ФАЙЛОВ
============================================================

По умолчанию workspace хранится в приватной директории приложения:
filesDir/workspaces/

Это обеспечивает простой доступ через обычный файловый API и удобную
интеграцию с JGit.

Импорт и экспорт: - ZIP; - Git clone; - Storage Access Framework.

Работу непосредственно с внешними папками через SAF оставить
дополнительным режимом. Возможности и скорость зависят от конкретного
DocumentProvider.

Все операции с файлами должны проходить через единый WorkspaceManager:

Agent -> ToolExecutor -> WorkspaceManager -> FileSystem

Ни один инструмент агента не должен самостоятельно открывать
произвольный путь.

WorkspaceManager обязан: - нормализовать и проверять пути; - запрещать
выход за пределы корня workspace; - корректно обрабатывать “..”,
абсолютные пути и символьные ссылки; - учитывать гонки при изменении
файлов; - проверять тип объекта и права доступа; - ограничивать размер
читаемых и записываемых файлов; - не следовать символьным ссылкам за
пределы workspace; - безопасно обрабатывать имена файлов и архивы при
распаковке.

Одной проверки startsWith() недостаточно. Нужны проверки канонического
пути и символьных ссылок. Для операций записи по возможности
использовать временный файл и атомарную замену.

Безопасность: - API-ключи не попадают в логи, crash reports и экспорт по
умолчанию; - ключи шифруются с использованием ключа, защищённого Android
Keystore; - текст файлов и веб-страниц рассматривается как недоверенные
данные; - агент не может выйти за пределы workspace; - опасные действия
требуют подтверждения; - архивы проверяются от path traversal; - сетевые
запросы ограничиваются политикой доступа.

Prompt injection нельзя считать полностью решённой одной системной
инструкцией. Нужны ограничения на уровне инструментов: недоверенный
контент не должен сам выдавать разрешения, менять политику безопасности
или инициировать запрещённые действия.

============================================================ 9.
CHANGESET И ПОДТВЕРЖДЕНИЕ ИЗМЕНЕНИЙ
============================================================

Не перезаписывать оригинальные файлы сразу после ответа модели.

Использовать промежуточную модель ChangeSet: 1. Агент формирует
предлагаемое изменение. 2. Приложение проверяет путь и исходное
состояние файла. 3. Изменение сохраняется как черновик. 4. Пользователь
видит Diff. 5. Пользователь применяет или отклоняет изменение. 6.
Приложение проверяет, что исходный файл не изменился с момента создания
Diff. 7. Изменение применяется безопасным способом.

Возможности: - принять или отклонить отдельное изменение; - принять или
отклонить весь ChangeSet; - показать построчный Diff; - показать сводку
добавленных и удалённых строк; - откатить применённое изменение; -
обнаруживать конфликт, если файл изменился после подготовки Diff; -
хранить историю изменений с привязкой к сессии и инструменту.

Это защищает пользовательские изменения и позволяет восстановиться после
сбоя.

============================================================ 10. ПРАВА И
РАЗРЕШЕНИЯ ============================================================

Для опасных операций предусмотреть три решения: - разрешить один раз; -
разрешить в этой сессии; - запретить.

Базовая политика: - чтение файлов внутри workspace — без вопросов; -
запись и изменение файлов — подтверждение; - сетевые запросы —
подтверждение или отдельная настраиваемая политика; - запуск команд —
отдельное подтверждение; - доступ за пределы workspace — запрещён.

Разрешения должны быть ограничены конкретными инструментами и областями
действия. Разрешение на одну операцию не должно автоматически давать
доступ к другим операциям.

В интерфейсе подтверждения показывать: - что именно будет сделано; -
какие файлы затронуты; - какие данные будут отправлены наружу; -
предполагаемые последствия; - возможность посмотреть Diff до применения.

============================================================ 11. ФОНОВАЯ
РАБОТА НА ANDROID
============================================================

Foreground Service полезен для длительных задач, но не гарантирует
бесконечную работу с выключенным экраном. Современный Android
накладывает ограничения на типы сервисов, разрешения, длительность и
фоновые сценарии. Поведение также зависит от производителя устройства.

Предусмотреть три режима:

1.  Активный — пользователь находится в приложении.
2.  Фоновый — задача продолжает выполняться с уведомлением, если это
    разрешено Android.
3.  Восстановление — после завершения процесса приложение
    восстанавливает сессию из Room и предлагает продолжить работу.

Сохранять состояние после каждого шага. Корректно обрабатывать отмену,
перезапуск процесса, потерю сети и ограничения батареи.

Не обещать пользователю гарантированную бесконечную работу агента в
фоне. Дать понятную справку по ограничениям Android и настройкам
батареи.

============================================================ 12. GIT И
TERMUX ============================================================

Git: - использовать JGit после проверки совместимости и
производительности на Android; - показывать status, diff и log; -
позволять создавать коммиты; - не выполнять destructive-команды без
отдельного подтверждения; - учитывать, что репозиторий может содержать
пользовательские незакоммиченные изменения.

Termux: - отложить до отдельного этапа; - интеграция должна учитывать,
что обычное Android-приложение не может свободно запускать произвольные
системные бинарники; - продумать обнаружение Termux, настройку
интеграции, передачу рабочей директории, stdout/stderr, таймауты и
завершение процесса; - не считать интеграцию универсальным локальным
shell без ограничений.

До появления Termux агент должен быть полезен как полноценный файловый
агент.

============================================================ 13.
КОНТЕКСТ И РАСХОДЫ
============================================================

Реализовать: - приблизительный подсчёт токенов; - обрезку слишком
длинных результатов инструментов; - контроль размера контекста; - сжатие
старой истории в краткое резюме; - сохранение важных фактов и решений
при сжатии; - лимиты расходов на сессию; - учёт токенов по
провайдерам; - отображение стоимости, если тариф известен.

Стоимость может быть неизвестна или меняться. Не показывать ложную
точность. Пользователь должен иметь возможность указать собственные
тарифы или отключить расчёт стоимости.

Сжатие контекста не должно удалять незавершённые вызовы инструментов,
важные результаты, решения пользователя и сведения о текущем состоянии
файлов.

============================================================ 14.
ДОПОЛНИТЕЛЬНЫЕ ВОЗМОЖНОСТИ АГЕНТА
============================================================

Plan Mode: - модель сначала формирует план; - показывает предполагаемые
шаги и файлы; - пользователь подтверждает план; - агент выполняет его
поэтапно; - при существенном отклонении от плана агент запрашивает
разрешение.

Автоматическое тестирование: - после изменений агент может предложить
запуск проверок; - на первом этапе — только через доступные
инструменты; - позднее — через Termux; - результаты тестов возвращаются
в контекст; - исправления снова проходят через Diff и подтверждение.

Вложения: - изображения и скриншоты ошибок; - PDF и текстовые
документы; - ZIP-архивы; - файлы проекта.

Роутинг моделей: - дешёвая модель для простых задач; - более сильная
модель для планирования и сложного анализа; - отдельная модель для
проверки изменений; - правила выбора моделей задаёт пользователь; -
приложение показывает, какая модель используется на каждом этапе.

Мультиагентность и роли Planner, Coder, Reviewer оставить на будущее. Не
усложнять первую версию параллельными агентами.

============================================================ 15.
ИНТЕРФЕЙС ============================================================

Стиль: - Material 3; - тёмная тема по умолчанию; - динамические цвета
Android; - один основной акцентный цвет; - минимум рамок и теней; -
достаточные отступы и скругления; - JetBrains Mono или аналогичный
моноширинный шрифт для кода; - спокойный гротеск для интерфейса.

Онбординг: 1. Выбор провайдера. 2. Ввод API-ключа. 3. Проверка
соединения тестовым запросом. 4. Выбор модели. 5. Первое сообщение.

Главный экран: - список чатов; - поиск; - группировка по дням и
проектам; - архивирование и удаление; - создание нового чата; -
переключение Чат / Агент.

Экран чата: - сообщения модели без тяжёлых пузырей; - лёгкое визуальное
выделение сообщений пользователя; - потоковый Markdown без мерцания; -
подсветка кода; - копирование и сохранение кода в файл; - компактные
карточки вызовов инструментов; - сворачиваемые блоки reasoning, если
провайдер их предоставляет; - перегенерация, редактирование, ветвление и
поделиться; - чип выбранной модели; - вложения; - кнопка отправки,
превращающаяся в «Стоп»; - дополнительный ряд клавиш для кода: Tab, Esc,
скобки и кавычки.

Экран агента: - вкладка Чат; - вкладка Файлы; - вкладка Изменения; -
вкладка Лог; - отображение плана и текущего шага; - прогресс
выполнения; - подтверждения опасных действий; - просмотр Diff; -
принятие и отклонение изменений; - создание Git-коммита.

Настройки: - провайдеры и ключи; - модели и их возможности; - системные
промпты; - пользовательские роли; - разрешения; - лимиты токенов и
денег; - история расходов; - внешний вид; - экспорт и импорт; -
резервное копирование.

Дополнительные детали: - haptic feedback; - predictive back; - плавное
появление текста; - адаптация под планшеты и складные устройства; -
понятные сообщения об ошибках на русском языке; - состояния пустого
экрана, отсутствия сети и исчерпания лимита; - русский и английский
языки; - доступность и масштабирование интерфейса.

============================================================ 17.
ТЕСТИРОВАНИЕ И КАЧЕСТВО
============================================================

Обязательные виды тестов: - unit-тесты доменной логики; - тесты
адаптеров провайдеров на сохранённых SSE-примерах; - тесты сериализации
и восстановления сообщений; - тесты миграций Room; - тесты
WorkspaceManager на traversal и символьные ссылки; - тесты ChangeSet и
конфликтов файлов; - тесты прав доступа; - тесты отмены и восстановления
агентного цикла; - UI-тесты критических сценариев; - тесты на слабой
сети и потере соединения.

Критические сценарии: 1. Пользователь отменяет генерацию. 2. Соединение
обрывается во время стрима. 3. Модель присылает некорректный Tool Call.
4. Пользователь отклоняет изменение. 5. Файл меняется после подготовки
Diff. 6. Android завершает процесс во время работы агента. 7.
Пользователь достигает лимита расходов. 8. Архив содержит попытку выхода
за пределы workspace. 9. Модель пытается прочитать файл за пределами
workspace. 10. API-ключ отсутствует или неверен.

============================================================ 18.
ПОДВОДНЫЕ КАМНИ
============================================================

-   Слабые модели могут плохо вызывать инструменты. Нужны строгая
    валидация, ограниченные повторные попытки и понятные ошибки.
-   API провайдеров меняются. Адаптеры должны быть изолированы и покрыты
    тестами.
-   Не все модели поддерживают инструменты, изображения и reasoning.
-   Стриминг длинного Markdown может тормозить Compose. Нужны пакетные
    обновления и кэширование.
-   Android и оболочки производителей могут завершать фоновые процессы.
-   Foreground Service не гарантирует бесконечную фоновую работу.
-   Запуск бинарников ограничен Android. Termux — отдельная интеграция,
    а не универсальный shell.
-   SAF зависит от реализации DocumentProvider.
-   Git может столкнуться с пользовательскими незакоммиченными
    изменениями.
-   Автономный агент способен быстро потратить много токенов. Лимиты
    должны быть включены по умолчанию.
-   Prompt injection нельзя решить только системным промптом. Нужны
    ограничения инструментов и разрешений.

============================================================ 20.
ПРИНЦИПЫ ПРОЕКТА
============================================================

1.  Сначала надёжность, потом количество функций.
2.  UI не обращается напрямую к сети и файловой системе.
3.  Все операции с workspace проходят через WorkspaceManager.
4.  Все изменения файлов проходят через ChangeSet и Diff.
5.  Опасные действия требуют явного разрешения.
6.  Агент ограничен бюджетом, временем и количеством шагов.
7.  Состояние агента сохраняется после каждого значимого действия.
8.  Провайдеры изолированы адаптерами.
9.  Неизвестная стоимость не отображается как точная.
10. Новые возможности добавляются без разрушения существующей
    архитектуры.

ИТОГ

Продукт — локально работающая Android-среда для общения с разными
ИИ-моделями и безопасной агентной разработки. Его главные преимущества:
независимость от провайдеров, работа с собственными API-ключами,
локальные рабочие пространства, прозрачные изменения файлов и контроль
расходов.

Главный приоритет первой версии — не максимальное количество функций, а
качественный чат и надёжный файловый агент, которому пользователь может
доверять.
